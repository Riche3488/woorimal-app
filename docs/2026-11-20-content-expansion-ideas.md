# 콘텐츠 확장·경험 개선 방안

작성일: 2026-11-20 · 상태: 1~2단계 중 C1(자동분)·C2(방법 B)·C3(출제)·E5 구현함 → [구현 기록](superpowers/specs/2026-11-20-content-quality-1.md). 3단계 C4·E2·E4 구현함 → [구현 기록](superpowers/specs/2026-11-20-word-card-collection-reminder.md). 나머지는 제안

웹 저장소 `D:\projects\woorimal_contest`가 이미 가진 자료로 앱의 콘텐츠를 넓히고 풀이 경험을 낫게 할 방법을 정리했다. 수치는 2026-11-20 웹 저장소의 `public/app/pack.json`·`data/`를 `node -e`로 센 값이다.

## 1. 지금 확인한 사실

### 앱 묶음(`public/app/pack.json`, 6,120문제)

| 유형/출처 | 문제 수 | 해설 없음 |
| --- | ---: | ---: |
| 첫소리 `chosung` (original 698 · adapted 2,123) | 2,821 | **2,771** |
| 뜻 보고 낱말 `meaning` (original 708 · adapted 1,463) | 2,171 | 658 |
| 띄어쓰기 `spacing` (blog 322 · adapted 256) | 578 | **568** |
| 맞춤법 `spelling` | 351 | 123 |

| 쓰임 `usage` (보통·어려움 20 포함) | 66 | 0 |

여기서 드러나는 것:

1. **문제 열 개 중 일곱 개에 해설이 없다.** 앱은 틀리면 해설을 읽고 넘기게 만들었는데(retention-1), 대부분은 정답만 보고 지나간다. "틀린 문제를 다시 보지 못해 실력이 늘지 않음"이라는 설계 문서의 실패 조건에 가깝다.
2. **84%가 직접 입력하는 문제다**(첫소리·뜻·속담 5,125개). 대회 준비생에게는 맞지만, 지하철에서 한 손으로 푸는 출퇴근 사용자에게는 무겁다.
3. **같은 낱말이 여러 유형으로 겹친다.** 정답 낱말은 5,043개이고, 그중 736개가 두 유형 이상에 나온다. 예를 들어 `meaning:2`와 `chosung:2`는 둘 다 "가늘다"의 뜻풀이에 초성 힌트까지 보여 주는 사실상 같은 문제다. `src/core/picker.ts`는 문제 키로만 중복을 거르므로 한 판에 같은 낱말이 두 번 나올 수 있다.
4. 난이도 `level`(보통·어려움 20문항)이 묶음에 있지만 앱 화면에서 따로 고를 수 없다.

## 2. 제안 — 콘텐츠

우선순위는 **비용 대비 체감**으로 정했다. ★이 많을수록 먼저 한다.

### C1. 해설 채우기 ★★★ (웹 저장소만 고치면 됨, 앱 수정 없음)

앱은 이미 `explain`을 보여 준다. 웹 `scripts/lib/app-pack.mjs`에서 묶음을 만들 때 비어 있는 해설을 가진 자료로 채운다.

| 유형 | 채울 내용 | 재료 |
| --- | --- | --- |
| 첫소리·뜻(낱말 기반) | `‘가늘다’ · 형용사 · 순우리말` + 예문 | `words.json`의 품사·어원·예문 |
| 첫소리·뜻(adapted) | 품사 + 문제에 안 쓴 다른 뜻 1~2개("이런 뜻도 있어요") | `dict.json`의 여러 뜻 |
| 속담 | 속담 전체 문장 + 뜻 | 원본 `meaning` |
| 띄어쓰기 | 규칙 요점 한 줄(의존 명사 '수'·보조 용언·단위 명사 등) | 사람이 쓰거나, 규칙 태그를 달고 태그별 설명문을 붙임 |

- 자동으로 채울 수 있는 것(첫소리·뜻·속담, 약 3,500개)부터 하고, 띄어쓰기 568개는 규칙 태그 20~30개로 묶어 설명문을 재사용하면 손이 덜 든다.
- 형식 변경이 없으므로 웹을 배포하면 기존 앱도 원격 묶음으로 바로 받는다.
- 나중에 해설을 문자열 대신 `{ pos, origin, example, more }`처럼 구조화하면 해설 카드를 더 보기 좋게 그릴 수 있다. 이것은 형식 변경이므로 `types.ts`와 함께 고친다(4장).

### C2. 보기형 뜻 문제 ★★★ (입력형 부담 줄이기)

입력형 낱말 문제를 **보기 4개 고르기**로도 낼 수 있게 한다. 오답 보기는 같은 품사·비슷한 글자 수의 다른 정답 낱말에서 뽑는다(웹 `mock.mjs`의 보기 생성 방식 참고).

- 방법 A: 웹이 묶음에 `choice` 버전을 따로 싣는다(문제 수가 늘어 보이지만 같은 낱말 중복이 커짐).
- 방법 B(추천): 앱이 출제 시점에 입력형 문제를 보기형으로 바꾼다(`src/core/`의 순수 함수, 테스트 먼저). 설정에 "입력 대신 보기로 풀기"를 두고, 처음 쓰는 사람은 보기형부터 시작해 익숙해지면 입력형을 섞는다. 묶음 형식은 그대로다.
- 오답 보기가 정답과 뜻이 같은 경우(동의어)를 막아야 한다. `synonyms`가 거의 비어 있으므로(2개) 같은 뜻풀이를 가진 낱말은 보기에서 뺀다.

### C3. 낱말 하나를 학습 단위로 ★★

같은 낱말이 첫소리·뜻 두 유형으로 나오는 것을 정리한다.

- 출제: 한 판에 같은 정답 낱말을 두 번 내지 않고, 최근 며칠 안에 본 낱말은 뒤로 미룬다(`picker.ts`).
- 웹 묶음: 원본이 같은 `meaning:N`·`chosung:N` 쌍(약 700개)은 문제 문장이 거의 같으므로 하나만 싣거나, 첫소리 쪽을 "초성만 보고 맞히기"처럼 실제로 다른 문제로 만든다.
- 외움 판정도 문제 키가 아니라 낱말 기준으로 묶으면 "외운 낱말 N개"라는 숫자가 정직해진다.

### C4. 오늘의 낱말 카드 ★★ (`original-content.json` 36개)

웹 자체 학습 낱말은 제목·쓰임 설명·팁·예문 2개·보기별 이유를 갖춘 가장 풍부한 자료다. 지금은 쓰임 문제 66개로만 들어온다.

- 홈에 "오늘의 낱말" 카드 하나: 읽고 → 바로 그 낱말 쓰임 문제 1~2개.
- 이 낱말을 틀렸을 때 해설 대신 카드 전체를 보여 준다.
- 36개라 하루 하나면 한 달 남짓 쓴다. 자체 제작 낱말을 늘리는 웹 작업과 같이 커진다.
- 묶음에 `cards` 배열을 선택 필드로 더한다(4장).

### C5. 가로세로 퍼즐 ★★ (26판, 자체 제작)

- 휴대폰에서 12×12판은 칸이 작다. 판을 그대로 쓰되 **단어 하나씩 확대해서 푸는 방식**(단서 → 입력 → 판에 채워짐)이 숏폼과 맞는다. 화면은 판 전체를 작게, 입력은 아래에서.
- 판마다 주제가 있어 "테마 한 판"으로 홍보하기 좋다.
- 웹 공개 허용 목록(`crosswordIds` 8판)과 앱 공개 범위를 같이 쓸지 따로 둘지 정해야 한다. 나머지 18판의 검수 상태를 먼저 확인한다.
- 화면이 새로 필요하므로 C1~C3보다 크다. 묶음에 `crosswords` 선택 필드를 더한다.

### C6. 실력 진단과 도전 모드 ★

- 첫 실행 때 자체 평가(3개)나 보통·어려움 문항으로 10문제 진단 → 처음 출제 난이도를 정한다(지금은 유형별 20번까지 쉬운 문제부터).
- 기록 화면에 "어려움 도전" 진입: `level: 'hard'` 문항만 모은 판. 지금 20문항뿐이라 웹에서 어려움 문항이 늘어난 뒤에 연다.

### C7. 낱말 정보로 만드는 가벼운 새 유형 (선택)

`words.json`의 어원·품사로 검수 부담이 적은 빠른 문제를 만들 수 있다.

- "순우리말일까, 한자어일까?" OX(어원이 적힌 591개)
- 품사 고르기, 속담 빈칸 보기형

빠른 OX는 연속 정답 보너스를 살리고 한 판 템포를 올린다. 다만 어원 자료가 정확한지 표본 검수가 먼저다. 틀린 정보가 퀴즈가 되면 해가 크다.

## 3. 제안 — 경험

### E1. 틀렸을 때의 1초를 학습으로 ★★★

C1과 짝을 이룬다. 해설 영역을 "정답 · 품사/어원 · 예문 · 다른 뜻" 순서의 작은 카드로 정리하고, ⭐ 담기를 그 카드에 둔다. 해설이 없던 문제가 많아 지금은 이 순간이 비어 있다.

### E2. 곳간에 쌓이는 것은 낱말 ★★

지금은 낱알·레벨만 쌓인다. 외운 낱말(C3 기준)을 곳간의 "낱말 도감"으로 보여 주면 성장 은유와 실제 실력이 이어진다. 유형·주제·어원별로 칸이 채워지는 모습은 대회 준비생에게 "얼마나 알게 됐나"를 보여 준다. 저장은 기존 `progress`에서 계산할 수 있어 새 저장 항목이 거의 없다.

### E3. 주제 묶음 ★

퍼즐 주제, 품사, 어원, adapted 문제의 소제목 성격(예: "순우리말 형용사")으로 "주제 한 판"을 만든다. 유형별 연습 옆에 둔다. 주제 태그는 웹 묶음 생성 때 붙인다.

### E4. 매일 다시 열게 하는 알림 ★

서버 없이 기기 안에서 예약하는 로컬 알림(`expo-notifications`). "오늘 복습할 문제 4개", "연속 기록 🔥 12일이 오늘 끊겨요" 정도로만 쓴다. 하루 한 번, 사용자가 시각을 고르고 끌 수 있게. 서버 쓰기 없음 원칙에 맞는다.

### E5. 문제 신고 (서버 없이) ★

1차 앱은 서버 쓰기가 없으므로, 해설 카드의 "문제가 이상해요"는 문제 키와 묶음 버전을 담은 메일 쓰기·공유 시트를 연다. 자동 생성 해설(C1)·보기(C2)를 넣으면 오류가 생길 수 있어 안전망으로 필요하다.

## 4. 묶음 형식을 바꿀 때

`CLAUDE.md` 규칙대로 웹 `scripts/lib/app-pack.mjs`와 앱 `src/core/types.ts`를 함께 고친다.

- **선택 필드 추가로만 넓힌다.** `cards`, `crosswords`, 문제의 `word`(낱말 단위 묶기용)·`tags`(주제)처럼 없어도 되는 필드를 더하면 옛 앱은 무시하므로 `minApp`을 올리지 않는다. `src/core/pack.ts`의 `parsePack`은 필드 허용 목록으로 거르지 않으므로(2026-11-20 확인) 모르는 필드가 있어도 묶음을 거절하지 않는다.
- `explain`을 문자열에서 객체로 바꾸는 것처럼 옛 앱이 잘못 읽을 변경만 `APP_PACK_MIN_APP`을 올린다. 가능하면 `explain` 문자열은 두고 `explainParts`를 새로 더한다.
- 묶음 크기: 지금 약 2MB. 퍼즐 26판·카드 36개는 수십 KB라 문제없지만, C2를 방법 A로 하면 크게 는다. 방법 B를 추천하는 이유 중 하나다.

## 5. 하지 않는 것

- 방송 회차 화면·방송 원문 문장(`adaptKbs: true` 유지). 대회 단계 구성을 흉내 낸 모드도 방송을 떠올리게 하는 이름·모양은 피한다.
- 계정·순위표·광고·서버 쓰기(1차 원칙).
- 검수하지 않은 자동 생성 문제를 대량으로 싣는 것. 자동으로 만든 것은 표본 검수 → 신고 경로(E5)를 갖춘 뒤 연다.

## 정해야 할 것

- 입력형을 보기형으로 바꾸는 것을 기본으로 둘지, 설정으로만 둘지(대회 준비생은 입력형을 원함).
- 퍼즐 26판 중 앱에 낼 판의 범위와 검수 상태.
- 띄어쓰기 해설을 사람이 쓸지, 규칙 태그 템플릿으로 갈지.
